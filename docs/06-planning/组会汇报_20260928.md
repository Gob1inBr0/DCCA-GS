## 2. 渐进分层码流：从设计到全链路实测

| 层 | 内容 |
| --- | --- |
| 表示层 | 嵌套质量阶梯 + 分字段粗化档位（feat/offset 8 倍起步、scaling 2 倍起步，避免对数域悬崖） |
| 编码层 | 二值分解区间编码（零标志→符号→幅度逐位），基层/增强层用（组×粗值幅度桶）复合条件表，条件信息解码端可重算（零边信息契约，验证 100%） |
| 评测层 | 150 视角逐前缀渲染，逐视角数字存档；λ0.0005 / λ0.004 两族曲线 |

关键实测（1-78，150 视角）：渐进曲线 P0 15.75 MB@25.01 → 满精度
29.95 MB@26.70。与 base 单码率的差距全部定位在码流打包层（符号与 base
完全一致）——这引出了 B3（§3）。

两个负结果如实记录：

- **条件表细化（步长档位×分组变细）：未过门**（≥10% 字节目标，实测
  ±0.1% 噪声级）。结论：该编码架构下条件粒度已到顶。
- **学习式概率模型：四步全程证负关闭**。独立探针里 MLP 对"仅按组"静态
  表省 45.9%（过门），但接入生产码流后对"组×桶"复合条件表零增益。
  教训已入册：**门测量的参照基线必须与生产编码器同构**，否则高估增益。

## 3. B3 阶梯对齐训练：重启 → 双档过门 → 采纳

**问题**：渐进基层（8 倍粗化）失真大，P0 画质低。**方法**：训练末期
对量化符号到粗阶梯倍数的偏移加惩罚，把符号往基层友好的位置推。

过程有两次波折，都如实记录：

1. **代码丢失**：9-23 曾写了一半的改动以未提交修改的形式存在，在分支
   切换中丢失（当时记录"config 开关已加"失实，已更正）。重启后在正确
   的可运行代码线上重新实现，子代理审查抓出 mask 梯度泄漏等 2 个真 bug。
2. **v1 权重过猛判负**：w=0.05 时 P0 +0.093（门 +0.3 未过）且满精度塌
   0.48 dB。机制成立但代价过大——惩罚对属性的推力在 Adam 下不随权重
   线性缩放。

**v2 双档配对实验（同代码同种子，只差惩罚开关）双门通过**：

| 档 | P0 增益 | 满精度档 | 判定 |
| --- | --- | --- | --- |
| λ0.0005（w=0.01） | **+0.245**（150 视角实测 +0.256） | **+0.083** | 采纳 |
| λ0.004（w=0.05） | **+0.95**（150 视角实测 +0.86） | −0.026（噪声级） | 采纳 |

且 λ0.0005 档四档全面更好（P1–P3 同时省 1.2–4.1 MB）。两个附带发现：
机制收益随悬崖变陡而放大（紧档是主战场）；16 视角配对外推与 150 视角
实测差 ≤0.01 dB（快速口径可信）。

## 4. 与 HAC++ 的对比：延伸到低码率后的完整图景

补跑了 HAC++ 官方代码 λ0.008 / 0.016 两点（协议与已有三点一致）：

| λ | 体积 | PSNR |
| --- | --- | --- |
| 0.016 | 12.10 MB | 26.868 |
| 0.008 | 16.34 MB | 27.633 |

三层结论：

1. **HAC++ 紧档不塌**，曲线平滑延伸到 12.1 MB——"低码率区只有我们有
   产品"收缩为"<12.1 MB 独占"（λ0.004 渐进曲线从 7 MB 起步）。
2. **延伸段我方 base 全面占优**：27.394@10.67 对 HAC++ 26.868@12.10
   （高 0.53 dB 且小 1.4 MB）；27.695@13.90 对 27.633@16.34（同画质省
   2.4 MB）。
3. **渐进不打画质仗**：同字节下仍低于 HAC++ 1–2 dB，但 HAC++ 没有
   "一个文件多档"的能力；B3 把这个独占区的起点抬高了 0.86–0.95 dB。

高码率区（20–40 MB）的既有定位不变：base 对 HAC++ 同画质省约 30%
（可辩护口径：平价点 −24%、最近点对 −30.6% @ −0.146 dB）；BD-rate
数字维持冻结（双方画质区间不重叠，单一数字是外插伪影）。
