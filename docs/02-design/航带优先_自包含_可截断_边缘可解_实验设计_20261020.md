# 航带优先 + 自包含 + 可截断 + 边缘可解：UAV 大场景实验设计

> 建立：2026-10-20。定位：UAV 大场景系统论文的实验设计，不是 CVPR 压缩 SOTA 论文。

## 0. 一页结论

**要验证的主张**：在无人机航拍场景里，把 DCCA 的单文件渐进码流改成“全局粗层 + 航带顺序瓦片细化”，可以让操作员用更少字节先拿到**航带沿线可用**的画面，同时保持“任意前缀解出完整场景、满精度逐位一致、解码不依赖任何学习模型”。

**三个就绪点**（本文的核心定义）：

| 就绪点 | 含义 | 字节 |
|---|---|---|
| **整景就绪** | 全局粗层（所有瓦片的 L0）收完，整景可渲染但粗糙 | `B_scene` |
| **航带就绪** | 航带命中的瓦片细化到目标画质，其余瓦片仍是粗层 | `B_route` |
| **满精度** | 所有瓦片细化完，与全局 DCCA 满精度逐位一致 | `B_full` |

**与全局顺序的差别**：全局顺序把字节平均花在所有瓦片上；航带顺序把航带瓦片先细化。总字节不变，但 `B_route` 明显更小，`TTFF_route` 更早。

**推荐判定标准（先写死）**：
1. 同航带画质下，`B_route` 比全局顺序至少省 **40%**；
2. 10 Mbps 下 `TTFF_route` 不超过全局顺序的 **50%**；
3. `B_full` 相对全局 DCCA 的开销不超过 **5%**；
4. 航带区域 PSNR 相对全局同字节点掉不超过 **0.2 dB**；
5. 瓦片接缝带 PSNR 相对内部掉不超过 **0.2 dB**；
6. 边缘设备上航带就绪解码不超过 **10 s**、峰值内存不超过满精度的 **1/4**。

任何一条不达标，按 §9 的退出条件处理；不硬写“航带优先有效”。

## 1. 问题与术语

### 1.1 现状数字

【事实】`全数据集上各方案结果.csv` 的 20 个 UAV 场景里，HAC++ 平均 **28.605 dB @ 15.85 MB**，3DGS/gsplat 平均 **28.005 dB @ 609.5 MB**；HAC++ 单景 6.69–21.32 MB、26.42–32.73 dB，场景差异很大。

【事实】DCCA 在 3 个有同协议点的场景：

| 场景 | DCCA | HAC++ | 差值 |
|---|---|---|---|
| 1-78 | 27.8125 @ 19.944 | 27.1403 @ 17.227 | +0.67 dB / +15.7% MB |
| 2-06 | 28.0911 @ 16.435 | 28.5076 @ 21.032 | −0.42 dB / −21.9% MB |
| 4-10 | 28.6951 @ 15.727 | 28.7555 @ 17.419 | −0.06 dB / −9.7% MB |

结论：DCCA 在 UAV 场景不是全面 SOTA，而是“**同画质更小 / 同字节更高**”的 rate–size 取舍；现有 DCCA 是**全局顺序**——所有瓦片平均推进，航带沿线不会优先变清晰。

### 1.2 术语

| 术语 | 定义 |
|---|---|
| **瓦片** | 按场景水平包围盒切出的空间块；锚点按中心落入瓦片；瓦片有重叠带（0% 或 5%） |
| **航带** | 按相机轨迹（或图像名顺序）得到的瓦片访问序列；同一航带内的瓦片按首次被相机看到的顺序排列 |
| **全局粗层 G0** | 所有瓦片的最粗精度层（L0）；收完 G0 即“整景就绪” |
| **瓦片细化块** | 某瓦片的 L1–L3 层；按航带顺序排列 |
| **航带就绪** | G0 + 航带命中瓦片的细化块；其余瓦片仍用 G0 粗层渲染 |
| **满精度** | G0 + 所有瓦片细化块；与全局 DCCA 满精度逐位一致 |
| **自包含** | 码流不依赖任何学习模型、哈希网格、码本或字典；只有 JSON 头 + 静态频率表 |
| **边缘可解** | 在无 GPU 模型文件的边缘设备上，只靠码流 + 解码器即可解出航带就绪画面 |

### 1.3 与现有工作的区别

- HAC++/contextgs/PC-GS：全局单码率文件；没有航带优先，也没有“任意前缀完整场景”。
- PCGS/ProGS/SCAR-GS/GoDe：渐进，但带学习式侧信息；层是全局空间/精度层，不是航带瓦片层。
- DCCA：已有“精度层 + 零模型 + 字节前缀”，但没有空间瓦片和航带顺序。
- 本文：在 DCCA 上增加 **G0 + 航带顺序瓦片细化**，把“质量轴”与“空间轴”分开；这是 UAV 特有的组合。

## 2. 系统设计

### 2.1 编码端

1. **瓦片划分**：按场景水平包围盒做规则网格（K=4/16/64）；**每个锚点只归属一个瓦片**（按中心落入）；0% 或 5% 重叠带只用于边界渲染/上下文，**不重复编码锚点**。
2. **航带顺序**：若图像名已是飞行时间序，直接按相机中心序列；否则按相机中心做最近邻路径。对每个瓦片记录首次被相机看到的顺序，得到 `route_order`。同时保留 `morton_order` 与 `random_order` 作为对照。
3. **全局粗层 G0**：所有瓦片各写一份 L0（锚点不重复）；这是“整景就绪”的边界。
4. **瓦片细化块**：按 `route_order` 写每个瓦片的 L1–L3；每个瓦片块内有 `[len][tables][payload]`，块头记录瓦片 id、层范围、字节长度。
5. **头**：JSON，含瓦片 bbox、瓦片顺序、每瓦片层偏移、字段阶梯、静态表位置；不含任何学习模型。
6. **自包含**：静态表随块内联；量化步长由解码端从已解码数据重算；不传模型/哈希/码本。

### 2.1.1 航带信息从哪里来

先区分两个词：

- **航道/航线**：项目文档里的“无人机 4 航道（远近×高低）”是**采集协议分类**，不是本文的“航带”。
- **航带**：无人机实际飞过的一条（或一组）航线；本文要的是**相机沿航带依次看到的瓦片顺序**，即 `route_order`。

航带信息按可靠性从高到低有五种来源：

| 来源 | 拿到什么 | 可靠性 | 1-78 现状 |
|---|---|---|---|
| **飞控日志 / GPS / IMU** | 时间戳、经纬度、高度、航向、云台角 | 最高（真实航迹） | 未见；需向采集方要 |
| **照片 EXIF** | `DateTimeOriginal`、`GPSLatitude/Longitude`、`GPSAltitude`、云台 yaw/pitch | 高（如果相机开了 GPS） | 待查；数据当前不在可见存储 |
| **COLMAP / SfM 位姿** | 相机中心、图像名、内外参 | 中（几何代理，不是飞控日志） | 有（`sparse/0/images.bin`，需恢复数据） |
| **操作员画的航线/ROI** | 一条折线或矩形区域 | 部署可用（人给的任务区） | 无；可作为演示 |
| **Morton / 随机顺序** | 空间局部性排序 | 对照，不是航带 | 可生成 |

**1-78 的具体取法**（数据恢复后）：

1. 用 `pycolmap` 读 `sparse/0/images.bin`，拿到每张图的 `name`、相机中心 `c2w`；
2. 若图像名是拍摄顺序（如 `DJI_0001.JPG` 递增），直接按名字排序；
3. 若名字不是时间序，按相机中心做最近邻路径（或轨迹平滑），得到一条几何代理航迹；
4. 对每张相机，按中心落入瓦片；按航迹顺序记录“瓦片首次被看到”的顺序，得到 `route_order`；
5. 画相机轨迹 + 瓦片访问图，人工检查是否有明显跳变/交叉；有交叉就改用分段/手动航线；
6. 如果 EXIF 里有 GPS/时间，用 GPS 轨迹替代第 3 步，并在论文里注明“真实航迹”。

**当前阻塞（事实）**：1-78 数据当前不在服务器可见存储里；`/dev/shm` 已清空，归档路径 `/mnt/newproject2/data/_archives/2-Architecture Complex/1-78.tar.zst` 当前不可见。**P0 第一件事是恢复 `1-78.tar.zst` 或确认你的本地/移动硬盘备份；没有数据就没有航带实验。**

**如果没有真实航带信息**：

- 用相机中心代理 + `morton`/`random` 两个对照；只有 `route` 同时赢过两者，才能说“航带顺序有效”，否则只能说“空间局部性有效”；
- 或用操作员手画航线（部署场景本来就可能没有飞控日志）；
- 或换一个有 GPS/EXIF 的公开 UAV 数据集做旁证（如 PIVOT 类数据），但主实验仍要 1-78；
- 论文措辞：没有飞控日志就写“flight-path proxy / camera-trajectory order”，不要写“真实航带”。

### 2.2 码流布局

```text
[header JSON]
[G0: tile_0 L0 | tile_1 L0 | ... | tile_{K-1} L0]          <- 整景就绪
[tile_route_0: L1 | L2 | L3]                                <- 航带瓦片 0 细化
[tile_route_1: L1 | L2 | L3]
...
[remaining tiles: L1 | L2 | L3]                             <- 满精度
```

- **前缀 1**：G0 结束 → 整景可渲染（粗）。
- **前缀 2**：G0 + 航带前 m 个瓦片 → 航带就绪；其余瓦片用 G0。
- **前缀 3**：全部 → 满精度；与全局 DCCA P3 逐位一致。
- 所有切点都在块边界；解码端按已收块重建；缺瓦片用 G0 粗层。

### 2.3 解码端

- 读头 → 读 G0 → 读航带瓦片块；只解码当前视锥/航带命中的瓦片；未命中瓦片用 G0 粗层。
- 渲染：所有瓦片的 G0 锚点 + 命中瓦片的细化锚点；保证画面完整，无洞。
- 边缘：CPU/constriction 解码；无模型文件；内存按“G0 + 命中瓦片”计。

### 2.4 “自包含”与“可截断”的验证

- 头里没有学习式权重/哈希/码本/字典；
- 解码端只用码流 + 静态表 + 固定公式；
- 每个块边界截断都能解码；
- 满精度与全局 DCCA P3 逐位一致；
- 航带就绪与“全局顺序同字节前缀”对比，验证不是靠额外字节。

## 3. 研究问题与假设

| 编号 | 问题 | 假设 | 证伪标准 |
|---|---|---|---|
| RQ1 | 航带顺序能否让航带区域更早达到目标画质？ | 同航带 PSNR 下，`B_route` 比全局顺序少 ≥40% | 3 景中 2 景 <20% → 航带顺序无价值 |
| RQ2 | 航带优先是否伤害整景/全局画质？ | 满精度与全局 DCCA 差 ≤0.1 dB；航带外区域不显著变差 | 满精度 >0.3 dB 或航带外 >0.3 dB → 失败 |
| RQ3 | 瓦片化是否带来不可接受的字节/接缝开销？ | `B_full` 开销 ≤5%；接缝带 PSNR 掉 ≤0.2 dB | 开销 >10% 或接缝 >0.5 dB → 需重叠/缝合或放弃 |
| RQ4 | 航带就绪能否在边缘设备上可解？ | 航带就绪解码 ≤10 s；峰值内存 ≤1/4 满精度 | >30 s 或 >1/2 满精度 → 边缘主张不成立 |
| RQ5 | 航带优先在真实带宽下是否值得？ | 10 Mbps 下 `TTFF_route` ≤全局顺序 50% | 3 档带宽中 2 档 <20% → 故事弱 |
| RQ6 | 这套东西是否只在 1-78 成立？ | 5–8 景中 ≥4 景方向一致 | <2 景 → 场景特定，降级为案例研究 |

## 5. 指标与评测协议

### 5.1 字节

- `B_scene`：G0 总字节；
- `B_route`：G0 + 航带命中瓦片细化字节；
- `B_full`：全部字节；
- `overhead = B_full / B_global − 1`；
- `route_gain = 1 − B_route(route) / B_route(global)`（同航带 PSNR 下）。

### 5.2 画质

- PSNR/SSIM/LPIPS：航带区域、非航带区域、整景；
- 接缝带：瓦片边界 ±N 像素的 PSNR，对比瓦片内部；
- 航带区域 PSNR 目标：`PSNR_full_route − 0.2 dB`；
- 整景满精度：与全局 DCCA P3 逐位一致（PSNR 差 ≤0.01 dB）。

### 5.3 延迟

`TTFF = 8·B / bandwidth + decode_time + render_time`。

- `TTFF_scene`：G0 到齐；
- `TTFF_route`：航带就绪；
- `TTFF_full`：满精度；
- 带宽：5/10/20/50 Mbps（UAV 下行典型档）；
- 解码/渲染在服务器与边缘设备各测一次；空闲机、预热后计时。

### 5.4 边缘设备

- 首选：Jetson Orin AGX/NX（如有）；否则 x86 CPU（固定核数）作代理，明确标注“Jetson 待测”；
- 指标：航带就绪解码 s、峰值内存 MB、是否只靠码流；
- 对照：全局顺序同字节前缀的解码时间/内存。

### 5.5 统计

- 瓦片/顺序实验不改训练，确定性；同一 checkpoint 下对比，不需要种子；
- 泛化场景每景 1 个种子；1-78 关键结论 2 个种子；
- 报告逐景与均值，不用平均值掩盖反例；
- 所有数字登记 `experiments.csv`；图从 CSV 生成。

## 6. 预先写定的判定标准

| 编号 | 标准 | 说明 |
|---|---|---|
| **G1 航带字节** | 同航带 PSNR 下，`route_gain ≥ 40%`，且 5–8 景中 ≥4 景 ≥30% | 主标准；不达标则航带顺序无价值 |
| **G2 航带时延** | 10 Mbps 下 `TTFF_route(route) ≤ 0.5 × TTFF_route(global)` | 部署主标准 |
| **G3 满精度** | `B_full` 相对全局 DCCA ≤ +5%；满精度 PSNR 差 ≤0.1 dB；逐位一致 | 不伤害原码流 |
| **G4 接缝** | 接缝带 PSNR 相对内部 ≤0.2 dB；5% 重叠可到 ≤0.1 dB | 瓦片化质量 |
| **G5 边缘** | 航带就绪解码 ≤10 s；峰值内存 ≤1/4 满精度 | 边缘主张 |
| **G6 泛化** | 5–8 景中 ≥4 景 G1 方向一致 | 不是 1-78 特例 |

**辅助观察（不设标准）**：航带外区域画质、瓦片头字节、G0 占比、航带长度敏感性。

## 9. 风险与退出条件

| 风险 | 概率 | 影响 | 缓解 | 退出条件 |
|---|---|---|---|---|
| G0 太大，航带节省有限 | 中 | 主标准失败 | 降低 G0 精度/分层 G0 | `route_gain <20%` → 放弃航带顺序 |
| 瓦片头/重叠开销 >5% | 中 | 满精度变差 | 减少瓦片数、头部压缩 | `overhead >10%` → 改 K=4 或放弃 |
| 接缝明显 | 中 | 画质/视觉 | 5% 重叠、接缝融合 | 接缝 >0.5 dB → 加重叠仍不行则放弃 |
| 边缘解码 >30 s | 高 | 边缘主张失败 | 并行/拆块、只解航带 | >30 s → 降级为“服务器端可解”，不写边缘 |
| 航带定义主观 | 中 | 可复现性 | route/morton/random 三对照；公开轨迹 | 只有 route 有效、morton 无效 → 说明是顺序效应，可接受 |
| **1-78 数据当前不可见** | 高 | 主实验无法开始 | 从 `/mnt/newproject2` 归档或你的备份恢复；确认 EXIF/COLMAP | 找不到数据 → 换公开 UAV 数据或暂停 |
| UAV 数据不能公开 | 高 | 复现性 | 匿名化/公开替代/补充材料 | 无法提供任何样例 → 论文降级为案例研究 |
| HAC++ PSNR 更强 | 高 | 审稿人质疑 | 故事写 rate–size–deployment，不写 SOTA | 5–8 景中 DCCA 全面落后 >1 dB → 改分析/UAV 基准 |

**总退出条件**：如果 P1 的 1-78 原型在 K=16 下 `route_gain <20%` 或接缝 >0.5 dB，停止航带优先，回到全局 DCCA/分析论文；不硬做。
