## 1. 严重发现：融合分数被 `mini_splat_full_selected` 门控跳过

### 1.1 Bug 机理

`hacplus/scene/gaussian_model.py` 的 SPA 投影中，融合分数块位于
`if getattr(self, "mini_splat_full_selected", False):` 之内，而该标志**只在
mini-splat-full（blur-split + 贡献面积简化）路径**（`scaffold_gs/hacpp.py`
`mini_splat_reinit` 的 full 分支）才置 True。我们所有融合实验都只开
`--cfg.model.fusion-prune`，没开 `--cfg.model.mini-splat-full` → 融合分数块从未执行，
剪枝分数退化为纯 `a + spa_u`（与 base 完全相同的 ADMM 打分）。

时间线（git 证据）：
- `d61e049`（minisplat-full 重构）引入门控；`4fa9303`（9/6 LYH 运行时同步进 repo）已含门控；
- `d3b4f49`（9/6 "覆盖约束修复"提交）在该门控结构上打补丁——修复脚本同样没开 full 模式；
- 9/5 的崩溃 run（fusion_s0@0.004 = 25.95 dB）发生在重构同步到 LYH 之前，融合当时真实生效，
  **崩溃是真实的**，作为负结果/动机仍然成立。

### 1.2 连带问题：字段错位

`fusion_sensitivity_weight`（配置/启动脚本在设，0.5）在融合代码里**从未被读取**；
代码读的是 `fusion_sensitivity_cap`（默认 0.3）。两个字段名并存且互不相通。

### 1.3 受污染的结果（全部降级为"base 复跑"）

| 运行组 | 标签含 | 实际语义 |
| --- | --- | --- |
| 1-78 covfix@0.004（27.573） | covfix | 纯 SPA + 覆盖约束（约束在 50 万锚点下近 no-op）≈ base 复跑 |
| 2-06 / 4-10 covfix@0.004、fusion@0.002/0.0005（泛化矩阵 6 点） | fusion/covfix | 同上，均为 base 复跑 |
| RD 图"融合剪枝·修复后"曲线与 **BD-rate −11.1%** | — | **归因无效，撤回**。base 与 covfix 的差（+0.06~+0.12 dB）在 run-to-run 噪声内（旧基线 27.42/27.64/27.98 vs 新基线 27.51/27.75/27.95 的复跑差 ±0.1 dB 可佐证）；窄共享区间会放大噪声 |

保留有效：**复杂度乘子（I2×I6）的全部消融**（i2off/i6off/base，均为纯 SPA，与门控无关）、
feat_dim 扫描、HAC++ 原版同协议 1-78 对比、25.95 崩溃（真实负结果）。
意外收益：这批"base 复跑"正好用作 **run-to-run 方差估计**（论文误差棒）。

### 1.4 修复（已验证）

1. `gaussian_model.py`：融合块移出 full 门控；`fusion_prune=True` 且覆盖信号就绪即生效；
   敏感度不可用时显式打印 `SENSITIVITY_UNAVAILABLE → coverage-only`（不再静默）；
   敏感度份额硬封顶 `min(w, 0.3)`（读取 `fusion_sensitivity_weight`，消除字段错位）；
   每次投影打印节流日志 `[FusionPrune] step=… engaged=1 N=… eff=0.30 cov_mean=… sens_mean=…`；
2. core `adjust_anchor` 新增 `importance_provider` 钩子：**在锚点增长之后、投影之前**刷新
   每锚点覆盖面积（保证数量对齐）；
3. `hacpp.py`/`trainer.py`：融合开启时按 `mini_splat_views` 确定性抽 8 个训练相机，
   每个投影周期重算 `compute_contribution_areas`（带异常捕获，瞬时 OOM 自动回退上一周期）；
4. `config.py`：`fusion_sensitivity_weight` 默认 0.5 → 0.3。

冒烟验证（1-78，400 步，GPU 6）：

## 2. 零侧信息 / 作弊点核查（结论：干净）

| 检查项 | 结论 |
| --- | --- |
| 复杂度乘子输入 | `build_formula_complexity_input` 只用锚点坐标、预测 scaling/offsets、mask——全部解码端可重算 ✅ |
| 编解码对称 | 乘子经共享模块 `hacplus/utils/codec_consistency.py` 同时服务编码与解码；全部 run `bit_exact_roundtrip=true` ✅ |
| I6 敏感度 | 梯度 EMA 仅训练期使用；`sensitivity_multiplier` 只用于监督目标构造（hacpp.py:1025），不在解码路径 ✅ |
| 敏感度数组随增长扩容 | 在 padding/prune 维护列表中（1425/1539 行）✅ |
| 融合/覆盖信号 | 仅训练期投影使用，不进码流；修复后带生效日志可审计 ✅ |
| appearance 过拟合 | 协议 `appearance-dim 0`，无逐图外观向量可拟合测试视图 ✅ |
| 负结果代码默认关 | `importance_weighted_loss`/`semantic`/`hierarchical` 默认 False，runner 不传 ✅ |
| 体积口径 | fp32 `total_MB` 九项分解（feature/scaling/offsets/masks/hash/mlp/bounds/header），与 HAC++ 原生口径一致；MLP 量化已移除 ✅ |
| HAC++ 对比溯源 | `/home/project2/HAC-plus` = 官方仓库 `github.com/YihangChen-ee/HAC-plus`（TPAMI'25）；1-78 同协议参考点为原版代码实测 ✅ |

遗留提示：`compute_contribution_areas` 每 100 步 8 视角深度渲染带来 ~8% 训练开销、
